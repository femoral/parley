# Run summary — the default view, and the one that has to be cheap
#
# `parley run status <run>`, mirroring `parley status <task>`: a ref promotes
# the list into a detail view. This is what an orchestrating agent reads on
# every loop iteration, so it is the view with a token budget.
#
# Example: the Research workflow, 32 tasks over two loop passes, blocked on
# loop-budget exhaustion (#217).

# -----------------------------------------------------------------------------
# THE POINT: one line per (node, iteration).
#
# 32 tasks - including a 6-wide and a 12-wide fan-out - render as 10 lines.
# The summary grows with the *shape* of the workflow times its loop passes, and
# is completely independent of fan-out width and of deliverable size. A Research
# run whose `scope` emits forty queries prints the same 10 lines.
#
# That bound is `nodes x max(loop.max)`, and both numbers are static in
# `workflow.json` - so `parley lint` can print the worst-case summary size
# before the run ever starts.
#
# Measured: this view is ~350 tokens.
#
# -----------------------------------------------------------------------------
# THE GIST COLUMN - structural rollup, zero inference.
#
# The map forbids daemon-side summarization, so a gist is composed from three
# deterministic parts, in order, joined by ` · `:
#
#   1. Enum out-ports, tallied.        `coverage=insufficient`
#                                      `verdict=2 approve, 1 changes_requested`
#   2. Plural out-ports, counted.      `41 sources`, `12 validations`
#   3. The child's own `summary`,      only when the node has exactly ONE task.
#      verbatim, truncated to the line.
#
# Plus `n/m ok` on any fan-out where n < m, so a lost sibling is never silent.
#
# Rule 3 is why `search` and `validate` show no prose: a 12-wide fan-out has
# twelve child-authored summaries and picking one, or merging them, is exactly
# the inference the map rules out. You zoom to read them (03-node-detail.txt).
#
# -----------------------------------------------------------------------------
# THE AUSTERITY THIS EXPOSES - see NOTES.md, N2.
#
# `validate` reads `12/12 ok · 12 validations`, which is nearly useless. What
# the orchestrator wants is `10 supports, 1 contradicts, 1 unreachable` - and
# the daemon *could* produce it, because `validation.status` is declared as an
# enum inside types/validation.schema.json.
#
# The draft deliberately refuses. The daemon tallies TOP-LEVEL enum ports only
# and never reaches inside a named schema type. Reaching in means the rollup's
# quality depends on how deeply someone nested a field, and there is no rule
# for which of five enum fields to tally.
#
# The consequence is a real authoring pressure: a step that wants a legible
# summary line must declare a top-level enum out-port. `adversarial-review`
# already does (`coverage`), which is why its line reads well and `validate`'s
# does not.

# `deliverables` ships IDs, never values - the whole point of the resolution
# split. `summary` is null on any multi-task node (gist rule 3). `tallies` and
# `counts` are the machine-readable form of the GIST column, so a UI or an
# agent recomposes the line rather than parsing it.
#
# `block.verbs` is on the wire because #218 made the verb set vary by reason
# (no `reject` outside a declared gate), and an agent should not be deriving
# that table itself.
